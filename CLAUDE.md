# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start Vite dev server on port 3000 (auto-opens browser). Client-rendered only: the prerender does not run here.
- `npm run build` — `prebuild` legal check, then `tsc` → `build:client` (`vite build`) → `build:ssr` (`src/entry-server.tsx` into `dist-ssr/`) → `build:html` (`scripts/prerender.mjs`) → `seo:check` (`scripts/seo-check.mjs`). Any step failing fails the Vercel deploy — that is the point. **Run it once at a time**: two builds in parallel wipe each other's `dist/`.
- `npm run preview` — `scripts/serve-dist.mjs`, a dependency-free emulator of `vercel.json` (redirects, `cleanUrls`, rewrites, real 404, headers) serving `dist/` on port 3000 with `strictPort`. `vite preview` would lie: its SPA fallback serves the prerendered home for `/perfil`.
- `npm run seo:check` — the SEO guardrail on its own, against the current `dist/`.
- `npm run seo:audit` — `tools/seo-audit/audit.mjs --base <url> --label <x>`: crawler view, HTTP matrix, Playwright, Lighthouse and PageSpeed Insights, written to `docs/seo/evidencia/<x>/` (not versioned). `tools/seo-audit/compare.mjs` diffs two runs and `smoke.mjs` runs the functional smoke tests. The tools under `tools/*` have their **own** `package.json` so nothing lands in the Vercel install: set them up with `npm --prefix tools/seo-audit ci` (not `install`, which makes npm inject the root package as a dependency).

There is no test suite and no lint script configured in this repo. Type errors surface via `npm run build` (or `tsc` directly); there is no separate lint step.

Requires a `.env.local` with `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` (see `.env.example`) — `src/lib/supabaseClient.ts` throws at import time if either is missing.

## Architecture

Helados Mados is a React SPA for a TikTok Live ice cream shop promo, backed by a real Supabase project (Postgres + Auth + Edge Functions): viewers redeem a "secret keyword" for a digital point + QR coupon, then redeem the QR in-store for physical stock and bonus points. Business logic that must be trustworthy (points, redemption limits, admin actions) lives in Postgres (RLS + `security definer` RPCs), not in client code.

**Backend: `supabase/migrations/*.sql` (applied in filename order) and `supabase/functions/`.** This is the source of truth for the data model and rules — read the migrations before assuming client code enforces anything:
- `profiles` — one row per `auth.users` row (`id` FK, `username` citext unique **but nullable**, `total_points`, `is_admin`, plus the profile fields `first_name`/`last_name`/`birthday_month`+`birthday_day`/`phone`/`email`/`avatar_url`/`whatsapp_opt_in`(+`_at`), `age_confirmed_at`, and the historical bonus flags `profile_bonus_awarded`/`google_bonus_awarded`, which nothing writes since `0040`). **The birthday has no year, on purpose (`0040`/`0042`):** only day and month, both or neither (CHECK `profiles_birthday_valid`, 29 Feb allowed); the old `birthdate` column was dropped with every stored year, and the privacy notice 4.0.0 says so — storing a year again needs a new legal version first. Two `auth` triggers feed it: `handle_new_user` (AFTER INSERT ON `auth.users`) creates the row, and `handle_identity_linked` (AFTER INSERT ON `auth.identities`) fills `email`/`first_name`/`last_name`/`avatar_url` from a Google identity. **`username` is null until the user finishes signing up at `/bienvenida`** — an OAuth signup has no username to offer, which is why the column had to become nullable. **`profiles.email` is only ever written by `handle_identity_linked`**: there is no client-facing path to it, and that is what guarantees every stored email is Google-verified.
- `dynamics` — the redeemable "keyword campaigns" (`keyword`, `starts_at`/`ends_at`, `physical_stock`, `physical_redeemed`); a DB exclusion constraint (`dynamics_no_overlapping_keyword`, surfaced as Postgres error `23P01`) prevents two active dynamics from sharing a keyword over overlapping date ranges
- `coupons` — one per user per dynamic, `status` (`active`/`redeemed`/`expired`), `digital_awarded`/`physical_awarded` flags
- RPCs (all `security definer`, executed via `supabase.rpc(...)` from the store): `redeem_keyword(p_keyword)` (validates the active dynamic, enforces one-coupon-per-user-per-dynamic, awards +1 point, inserts the `Coupon`), `scan_coupon` (admin-only via `is_admin()`; validates coupon status/expiry/stock, marks it redeemed, awards +10 points, increments `physical_redeemed`), `get_leaderboard(period)` (`'all'` sorts by `profiles.total_points`; `'day'`/`'week'`/`'month'` instead sum the points earned within the cutoff window — the +1 by `coupons.created_at`, the +10 by `coupons.redeemed_at` (migration `0039`; until then both counted on the coupon's creation date, so a QR scanned days after the keyword vanished from "today", "week" and often "month") — so per-period rankings can differ from all-time. **Ties go to whoever reached that score first** (the time of their last point in the window; in `'all'`, their last coupon point or, failing that, account creation), then by nickname — an owner decision (migration `0043`), and the only ordering: no client re-sorts. **It returns `username`, `points` and `es_tu_fila` — never the user's UUID.** It is granted to `anon` for the public Top 5, so returning the id published every account's internal identifier to anyone; `es_tu_fila` is computed server-side against `auth.uid()` and wrapped in `coalesce(..., false)`, because a bare `id = null` yields NULL, and Kotlin throws when deserialising null into a non-nullable Boolean), `username_available`, `is_admin()`, `complete_signup` (the whole account creation in one transaction — username, age declaration, legal acceptance and, if given, phone together; it refuses if the username is already set, so it cannot double as a rename tool, and it rejects any legal version it does not recognise), `update_my_profile(first_name, last_name, birthday_month, birthday_day, phone, whatsapp_opt_in)` (the only way a user writes their own profile; **takes no email parameter on purpose** and never touches `total_points`/`is_admin`/`username`; since `0040` it awards nothing). `claim_google_bonus` and `is_adult` were dropped in `0040`.
- `legal_versions` / `legal_acceptances` (migration `0022`) — which version of each legal document has been published, and who accepted what and when. `legal_acceptances` has **no FK to `profiles` on purpose**: it is the proof that consent existed, so it must survive account deletion. If it cascaded, deleting an account would destroy exactly the evidence. What is left is an orphan UUID that no longer resolves to anyone — the *bloqueo* the law contemplates, and the privacy notice declares it.
- `supabase/functions/redeem-keyword/index.ts` — a thin wrapper that forwards the caller's JWT and the keyword to `redeem_keyword`. It is kept because it is the endpoint both the web and the Android app call, and its contract (reasons in the body, also on non-2xx, which Android reads) is frozen.

**No IP address is stored anywhere in the database, on purpose (migrations `0035`–`0037`, 2026-10-07).** Redemptions used to be capped at 3 per IP per dynamic through `ip_redemption_logs`, a table of peppered SHA-256 hashes the edge function computed from `x-forwarded-for`. It was dropped together with the pepper secret: with Google-only sign-in and (back then) a mandatory, unique, write-once phone, a mass of accounts already cost a Gmail and a number each, and the cap was never a real lock anyway — `redeem_keyword` is granted to `authenticated`, so anyone with a session could call it directly with a fresh hash each time. Supabase Auth also writes the raw IP into `auth.sessions.ip` on every sign-in and refresh; there is no setting to turn that off, so the trigger `sesion_sin_ip` overwrites it with `0.0.0.0` before it is written (`0.0.0.0` rather than null so a future NOT NULL in GoTrue cannot break sign-ins). The privacy notice 3.0.0 says "No guardamos su dirección IP: ni en claro ni transformada" — **anything that starts storing an IP, raw, hashed or derived, makes it false and needs a new legal version first.** What remains is not ours: Supabase's and Vercel's technical logs see each request's IP, and the notice declares it.
- `account_deletions` (migration `0028`) — the log of deletions **executed by the team** (an admin or the superadmin — the `staff` role cannot delete accounts). Self-deletion is deliberately **not** logged: the holder acted themselves, the act is the request, and there is no third party to defend against; keeping the UUID of someone who asked to disappear would be retention without a purpose. Neither uuid column has an FK, for two different reasons — `user_id` points at someone just deleted, and an FK on `executed_by` would let an admin's own deletion destroy the record of everything they did. The `via` vocabulary names the *grounds*, not the actor (`admin_a_peticion`, `admin_prueba`), leaving room for the `admin_sancion` that the terms already contemplate.
- `supabase/functions/delete-account/index.ts` — account deletion, the ARCO right of Cancellation and a hard Google Play requirement. It needs the service role to delete from `auth.users`, and that key cannot live in Postgres within reach of a client-invocable function. **Who is being deleted comes from the JWT, never from the body** — accepting an id from the client would turn it into a delete-anyone endpoint by changing one field. It also requires an exact confirmation string (insurance against a miswired client, not security) and refuses personnel (any `role` other than `cliente`, reason still `admin_cannot_delete` for Android's frozen contract), since an admin who deletes themselves leaves the shop with nobody to scan coupons; the superadmin sets them back to `cliente` first.
- `supabase/functions/admin-delete-account/index.ts` — the same deletion, executed by an admin or the superadmin when someone asks by email (it reads `profiles.role`; staff gets `forbidden`, and any target that isn't `cliente` gets `target_is_admin`, a name kept for Android's frozen contract). **A sibling function and not a branch inside the other one, on purpose.** `delete-account`'s invariant is not a promise but a property of its shape: there is no parameter through which a victim can enter, verifiable by reading the file. Adding an admin branch would make that depend on an `if` staying in the right order forever — in the endpoint every client invokes with any user's JWT. Here the invariant is stated differently: the victim comes from the body because there is no other way, but **who executes comes from the JWT and never from the body**, which is exactly what the log has to be able to assert. Business rejections return **200** with `{success:false, reason}`, following `redeem-keyword`, because `functions.invoke` swallows 4xx bodies and the admin needs the actual reason on screen. The confirmation is **the target's typed nickname**, not a fixed string: that makes the check depend on who is being deleted, so a client dragging a stale id cannot delete the wrong person.

**`profiles.phone` is optional, editable and unique — since migration `0040` (2026-10-11), an owner decision.** Until then it was mandatory at signup and write-once (`phone_immutable`), as "un número, una cuenta" against one person farming a Live with several Gmail accounts. Now `/bienvenida` lets you skip it and `/perfil` lets you add, change or clear it. The partial unique index `profiles_phone_key` (`where phone is not null`) stays — one number cannot sit on two accounts, reported as `phone_taken` — but, being optional, it no longer stops anyone who simply leaves it blank; that was accepted knowingly. Without a number there is nowhere to send promos, so both RPCs return `optin_without_phone`, and both clients disable and untick the WhatsApp checkbox while the field is empty (not while it is half-typed: fixing a digit should not cost anyone their consent). The terms 3.0.0 and the notice 4.0.0 announce the change, and the legal gate shows it as "Gran noticia" (see *Legal text*).

**What counts as a valid phone lives in `public.phone_is_valid()` (migration `0021`), and nowhere else on the server.** The CHECK `profiles_phone_valid`, `complete_signup` and `update_my_profile` all call it, so the rule cannot drift between them. It is a whitelist by dialing code — today only `+52` followed by exactly 10 digits, the first of which must be 2-9 (no Mexican area code starts with 0 or 1, which also rejects the obsolete `+521` mobile prefix WhatsApp still displays). Adding a country is one `when` branch. Beware that a CHECK calling a function does **not** re-validate stored rows when the function changes: widening is safe, tightening needs a manual `validate constraint`.

The client mirror is `PHONE_COUNTRIES` in `src/lib/phone.ts`, consumed by the shared `PhoneField` component that both `/bienvenida` and `ProfileDataModal` render — **the two definitions change together**, and like the points economy, editing only the client changes nothing that is actually enforced. `PhoneField` keeps the dialing code as a fixed prefix and takes only the national digits, because the previous single free-text field made `+52` plus 9 digits indistinguishable from a valid number — that is exactly how one got stored. `phone.ts` also strips the stray leading `1` of a pasted `+52 1 ...`, since rejecting it would read as a bug; the server stays strict and only ever stores the canonical 10.

**Client state: `src/lib/store.ts`.** A Zustand store that's a thin async wrapper over Supabase — it holds `profile`, `isAdmin`, `authReady`, `dynamics`, `coupons`, `profiles`, and calls out to Supabase Auth / Postgres / the edge function for every action (`signInWithGoogle`/`logout`, `completeSignup`/`updateMyProfile`, `fetchDynamics`, `addDynamic`/`updateDynamic`/`deleteDynamic`, `redeemKeyword`, `scanCoupon`, `getUserCoupons`, `getLeaderboard`, `getLegalStatus`/`acceptLegal`, `deleteMyAccount`). Nothing is persisted to `localStorage` — `initAuth()` restores session state on load via `supabase.auth.getSession()`/`onAuthStateChange()`, so real auth state (not a mock store) is the source of truth across reloads.

**Auth: Google is the only way in, for signing up and for signing in — since 2026-09-30.** Until then the web kept a second door for the "legacy" cadets created before signup went Google-only: nickname + password, mapped to a synthetic email (`<username>@accounts.helados-mados.app`). That door is closed and the client code for it is gone — no password form, no `setPassword`, no link/unlink of Google. Two server-side pieces enforce it:
- *Enable Email provider* is **OFF** in the hosted dashboard, on purpose. GoTrue then rejects `signInWithPassword` with `422 email_provider_disabled` before looking at the password. `supabase/config.toml`'s `[auth.email] enable_signup` maps to that same toggle, so it is `false` there too. **Turning it back on reopens password login for every old account: their password hashes were deliberately kept.**
- The `before_user_created` hook (migration `0020`, `public.hook_google_only_signup`) still rejects any user creation whose provider is not `google`, as a second lock.

The sessions that legacy cadets still had open were deleted from `auth.sessions` once, on the cutover day, so nobody kept access through an old refresh token.

**What happened to the legacy accounts:** the 170 that never linked Google are untouched — row, nickname, points, coupons and hashed password — but nobody can sign in to them. They still show on the leaderboard and in Admin → Clientes, where a "Sin acceso" badge marks them (`profiles.email` is null ⇔ Google was never linked, because only `handle_identity_linked` writes that column). A former cadet who signs in with Google gets a brand-new account, and their old nickname reads as taken because their own dead account holds it; `/bienvenida` explains that in one folded line. **No recovery is promised anywhere, on purpose:** whoever wants their old account writes to contacto@, and the owner handles it case by case. A migration tool is a future decision, only if many people ask.

**Two auth settings in the hosted dashboard matter.** The global *Allow new users to sign up* must stay **ON**: it is instance-wide, not per-provider, and off it kills brand-new Google signups with `422 "Signups not allowed for this instance"` at `/callback`, which fails silently in the UI and costs signups every Live. *Allow manual linking* is **OFF** — it only existed so legacy cadets could link Google, and nothing calls `linkIdentity()` anymore.

Diagnosing auth failures: the client sees only a generic failure, so read `auth_logs` instead — `select log_attributes['error'] from logs where source = 'auth_logs' and log_attributes['path'] in ('/token','/callback')`.

**Roles (migration `0044`, 2026-10-12): `profiles.role` is `cliente` | `staff` | `admin` | `superadmin`, and it is the source of truth.** `profiles.is_admin` survives only as a *mirror* (`role in (admin, superadmin)`), kept by the trigger `profiles_rol_a_is_admin`, so whatever still reads the column keeps working untouched: Alexa's `estacion_voz` (prod-only, `alexa-feature` branch) and installed APKs. Never write `is_admin` by hand; the trigger overwrites it. Three server functions gate everything, none of them Supabase Auth roles:
- `is_staff()` (staff+) — `scan_coupon`, the three `estacion_set_*`, and the `coupons`/`estacion` SELECT policies (so the counter screens and their Realtime work with a staff session). Staff sees coupon rows (ids, timestamps) but not `profiles`.
- `is_admin()` (admin+) — dynamics CRUD, other people's `profiles`, legal acceptances, account deletions. Staff never passes it: no keywords of future dynamics, no customer panel.
- `is_superadmin()` — the `metricas_*` RPCs, `asignar_rol`, `marcar_excluir_de_listas`, and reading `cambios_de_rol`.

**Roles are only handed out by `asignar_rol(p_usuario, p_rol)`**, superadmin-only: it never creates a superadmin, refuses to touch oneself or another superadmin, refuses accounts without a nickname or legacy accounts without Google access, and logs every change to `cambios_de_rol` (no FKs, same reasoning as `account_deletions`). There is one superadmin (the owner's account, set by email in `0044`); a second one would be a migration, on purpose. Personnel never appear in the ranking (`get_leaderboard` filters `role = 'cliente'`) nor in Admin → Clientes, and can't delete their own account; to remove someone from the staff, the superadmin first sets them back to `cliente`. The client mirror is `src/lib/roles.ts` (`rolDe`, `alcanza`, `inicioDe`, `permisosDe`): the store derives `rol`/`isStaff`/`isAdmin`/`isSuperadmin` from it, and `ProtectedRol minimo=…` in `AppRoutes.tsx` sends anyone who falls short to their own start screen (staff → `/admin/scanner`). Android mirrors it in `core/data/model/Rol.kt`; there staff gets only Escáner + Perfil, and Métricas/roles are web-only.

**The privacy notice declares all of this (4.1.0):** staff only validates coupons and sees nickname + points on a scan; the customer list is admin+; statistics and promo lists are the responsable's (superadmin). Widening what a role sees needs a new legal version first.

**Data model & types: `src/lib/types.ts` + `src/lib/database.types.ts`.** `database.types.ts` is the generated Supabase schema (regenerate with the Supabase CLI/MCP after any migration); `types.ts` derives the app-level `Profile`/`Dynamic`/`Coupon` types from it.

**Routing: `src/AppRoutes.tsx`.** The route tree (`routeElements`) and the shell around it (`AppShell`: `initAuth`, `RouteTracker`, `BottomNav`, `CookieBanner`) live there so the same tree renders under `BrowserRouter` (`src/App.tsx`) in the browser and under `StaticRouter` (`src/entry-server.tsx`) at build time — see "SEO" below. Admin routes are wrapped in a local `ProtectedRol minimo=…` guard (waiting on `authReady` first): `staff` for the scanner, Estación and the counter screens, `admin` for `/admin/dashboard` and `/admin/users`, `superadmin` for `/admin/metricas`; anyone short of it goes to their own start screen, or to `/admin` if not personnel — the client-side guard is UX only; the real boundary is Postgres RLS + the RPCs' `is_admin()` checks. `ProtectedMember` additionally bounces anyone whose `profile.username` is null to `/bienvenida`; `redeem_keyword` enforces the same rule server-side (reason `no_username`), since a route guard alone would not stop a direct visit to `/generar`. `ProtectedMember` also wraps its children in `LegalGate`, which blocks on a pending legal version. It sits **inside** the guard rather than around the routes so `/terminos` and `/privacidad` stay reachable while the gate is up — otherwise it would be asking people to accept blind. If the status query fails it does **not** block: this is a legal requirement, not a security control, and bricking the app over a network blip is far worse than showing a new version late. `/terminos`, `/privacidad` and `/eliminar-cuenta` are public and unguarded on purpose: the notice has to be readable before an account exists, and Google Play requires a deletion URL reachable without installing the app.

`/auth/callback` (`AuthCallback.tsx`) is where every Google redirect lands — it routes to `/bienvenida`, a resumed `/generar`, or `next`.

**`/bienvenida` is the whole signup form, not just a nickname picker.** It collects the nickname, a declaration of being 18+, acceptance of the two legal documents and, optionally, the WhatsApp number. All of it lands in one `complete_signup` call, so no account can exist without a record of which text its owner accepted. Note this screen already sees real drop-off, so anything added here costs signups.

**Two checkboxes, and the split between them is the whole point.** The first bundles *18 años cumplidos* with *accepting both documents* — both are contract terms, neither is separable. The second, permission to message you on WhatsApp, is separate and **optional**: it is data processing for advertising, and until migration `0023` it was mandatory to create an account. That made the consent not *free* in the sense of LFPDPPP art. 2, and a consent that is not free is not consent — it would have dragged the whole privacy notice down with it. `complete_signup` no longer returns `consent_required`; it returns `age_required`, `legal_required`, `legal_incomplete` and `unknown_version` instead. **Never re-bundle the WhatsApp checkbox with anything mandatory.**

The `aviso de privacidad simplificado` is **one tap away**: a button right above the checkboxes — at the point of collection and before "Empezar", where Mexican law wants it — opens it in a modal. It comes from the same source as `/privacidad`, so it cannot drift from it. It used to render open by default (six paragraphs between the phone field and the button); the owner had it folded because of this screen's drop-off, so discuss before unfolding it again. The yellow "¿Ya tenías cuenta…?" note for former legacy cadets is folded to one line for the same reason. **Nothing long stays visible on `/bienvenida`.** Android still shows three paragraphs of the notice open — a known divergence.

The two checkboxes cannot be shortened away: `terminos.md` says the age declaration is made by ticking a box, and `privacidad.md` says WhatsApp consent is given (or not) by ticking another at signup. Removing either needs a new legal version, which makes every existing user accept again.

**Three auth entry points, all the same `GoogleButton`:** `src/pages/Login.tsx` (standalone), the auth step of `src/pages/Redeem.tsx` (`keyword` → `auth` → `success`, which exists only to finish an in-flight redemption), and `src/pages/admin/AdminLogin.tsx` (sends `next` = `/admin/dashboard`; a signed-in non-admin sees "no tiene acceso" and a sign-out button instead). The same button signs in an existing account and creates a new one, so there is no "are you new?" step anywhere. `Redeem`'s "Inicia sesión primero" shortcut links to `/login` rather than rendering another variant inline.

**The OAuth `redirectTo` must never carry a query string.** Supabase matches it against the Redirect
URLs allow-list by comparing the *whole* URL, query string included, so a `?next=...` fails to match an
exact allow-list entry. GoTrue then silently discards the `redirect_to` and falls back to the Site URL,
which is production — the symptom is a local login landing on the live site. `oauthRedirectTo()` in
`store.ts` therefore returns a bare `<origin>/auth/callback`, and anything that must survive the round
trip goes through `sessionStorage`: `src/lib/authIntent.ts` for the post-login destination, and
`src/lib/pendingRedeem.ts` for an in-flight redemption. That module pair is also why `AuthCallback`
takes no `next` parameter from the URL, which removes the open-redirect surface entirely.

**Any change of origin breaks the match the same silent way**, and the symptom never varies: a local
login lands on the live site. A dev server drifting to port 3001 does it, hence `strictPort: true`.

**Supabase also rejects any `http://` destination whose host is not `localhost` or `127.0.0.1`, even
when that exact URL is in the allow list.** This was verified directly against the project: of four
allow-listed URLs, `http://localhost:3000/auth/callback`, `http://127.0.0.1:3000/auth/callback` and
`https://heladosmados.com/auth/callback` were accepted while `http://192.168.1.80:3000/auth/callback`
was rejected. So opening the dev server from a phone over the LAN IP can never work, and adding that
IP to the allow list does nothing — `npm run phone` is the answer instead (see below).

Because the failure leaves no trace in the browser, `vite.config.ts` carries a plugin that prints, on
every `npm run dev`, which of the origins it serves are actually usable and which are not. To confirm a
suspicion from the server side, `auth.flow_state.referrer` stores the destination GoTrue *resolved* for
each attempt: the allow-listed URL means accepted, the bare Site URL means rejected and fell back.

**`npm run phone` (`scripts/phone-link.mjs`) is how the app gets tested on a real phone.** It uses
Android wireless debugging: it locates `adb` (which winget installs *without* putting on the PATH),
discovers the phone over mDNS, connects, and runs `adb reverse tcp:3000 tcp:3000` so the phone's own
`localhost:3000` points at this machine's dev server. The phone then browses to `http://localhost:3000`
— an origin Supabase accepts. Pairing is once per phone (`npm run phone -- --pair <ip:port> <code>`,
and the phone's pairing screen must stay open while it runs, or `adb pair` dies with `protocol fault`).

That also fixes a second problem for free: a LAN-IP origin is not a secure context, so `crypto.subtle`
is gone (PKCE quietly downgrades from `s256` to `plain`) and `getUserMedia` is blocked outright.
Reaching the phone through `localhost` restores both, so the QR scanner's camera works there.
`AdminScanner` still checks `window.isSecureContext` up front and points at its manual-UUID fallback,
because the raw camera failure reads as a permissions problem and sends you hunting in the wrong place.

One more: the PKCE `code` is single-use, so reloading a spent callback URL yields
`flow_state_already_used` — that is the link being used twice, not a bug.

**The OAuth redirect destroys the state of `Redeem`.** `keyword` and `step` live only in React state, so `src/lib/pendingRedeem.ts` stashes the keyword in `sessionStorage` before the browser leaves for Google; `AuthCallback` routes back to `/generar` and `Redeem` rehydrates and finishes the redemption on its own. Anything new that sends a user through OAuth mid-flow needs the same treatment.

**Admin flow:** `AdminLogin.tsx` → `AdminDashboard.tsx` (manage `Dynamic` campaigns via `addDynamic`/`updateDynamic`/`deleteDynamic`) and `AdminUsers.tsx` (browse `profiles` via `fetchAllProfiles`) → `AdminScanner.tsx` (camera-based QR scanning via `html5-qrcode`, calls `scanCoupon`). The scanner has a manual UUID-entry fallback (`<details>` block) for testing without a camera/second device. `AdminEstacion.tsx` (the fifth admin nav item) controls the counter screens below. Each role gets its own `BottomNav` (`ITEMS_POR_ROL`): staff sees Inicio/Escáner/Estación; the superadmin swaps Inicio for Métricas so five labels fit.

**Métricas (`/admin/metricas`, superadmin only, migration `0045`).** Everything is computed in Postgres by the `metricas_*` RPCs (`resumen`, `serie`, `horarios`, `dinamicas`, `clientes`, `lista`); the browser only gets numbers and short lists, never the profiles or coupons tables. They share the filters `p_desde`/`p_hasta` (a `[desde, hasta)` range), `p_dinamicas` (uuid[] or null) and `p_segmento` (`todos`/`whatsapp`/`nuevos`/`recurrentes`), count only `role = 'cliente'`, use Mexico City days, and place each point when it was earned, like the ranking (`0039`). The page keeps its filters in the URL (shareable, reloadable), and its fetchers live in `src/lib/metricas.ts` rather than the store, so the store — imported everywhere — doesn't carry them; `recharts` is likewise only in that route's chunk. Chart colors were validated with the dataviz skill's `validate_palette.js` (`src/components/metricas/comun.tsx`); every chart has a table twin. **The promo lists (`metricas_lista`) are a voluntary purpose of notice 4.1.0:** they only hand out a phone when the customer gave WhatsApp consent, and skip anyone with `excluir_de_listas` (set by the superadmin when someone asks by email; the aggregate figures still count them, since they identify nobody). The Equipo tab is where roles are assigned, with its log.

**Counter screens (*pantallas de mostrador*): `/admin/leaderboard` and `/admin/flavors`.** Vertical 1080×1920 monitors in kiosk mode inside the store, signed in as staff or above (staff can run them since `0044`). They fill exactly the screen height and never scroll; every size is in `vh` so they read from a distance on any portrait monitor. `src/lib/kiosco.ts` hides `BottomNav` and the cookie banner on them — nobody answers a banner on a wall, and no answer means no measurement, which is what the notice promises. **`/admin/leaderboard` updates live, on purpose:** a customer who cashes their QR at the counter must see their +10 on the wall right then. `coupons` is in the `supabase_realtime` publication (`0043`) and `suscribirMarcador()` in the store fires on every redemption and scan (RLS means only an admin receives other people's coupons); the screen ignores the payload and re-reads `get_leaderboard`, batching bursts into one read, and still polls every minute as a backstop. A screen only picks up new code when reloaded. The leaderboard shows **only nickname and points**, like the public one: the privacy notice says profile photos are shown on no screen, and no titles (Comandante, Piloto…) because they were never defined.

**Rotated variants: `/admin/flavors_90`, `/admin/flavors_270`, `/admin/leaderboard_90`, `/admin/leaderboard_270`.** For a landscape TV mounted on its side whose system cannot rotate its output — the Fire TV Stick. `_90`/`_270` is the clockwise turn of the content, and which one applies depends on which way the TV was mounted. They are `KioscoGirado`, which frames the normal screen in a same-origin `<iframe>` of `100vh × 100vw`, rotated. **An iframe, not a `rotate` on the view**: `vh` is always the TV's real height, so a rotated view comes out at 56 % size, and inside the iframe the viewport is the iframe's, so the view renders untouched as on a portrait monitor. The `ProtectedAdmin` guard sits on the outer page so a missing session sends the *top* window to `/admin` — Google refuses to load inside an iframe. For the same reason `KioscoMarco`'s hidden exit link gets `target="_top"` when framed.

**`/admin/estacion` decides what those screens show, live.** The state is one row in `public.estacion` (migration `0033`): the leaderboard period and the *hidden* flavors. Hidden rather than visible on purpose, so a flavor added to the catalog shows up by itself. Admin-only RLS for reading, no write policies: only `estacion_set_periodo` / `estacion_set_sabor` / `estacion_mostrar_todos` write, and each checks `is_admin()`. The row is in the `supabase_realtime` publication; `suscribirEstacion()` in the store reads it, listens for changes, and re-reads it on (re)subscribe, on becoming visible and every 3 minutes, because changes made while disconnected don't come down the channel. That's why the screens never need a reload. The period only drives `/admin/leaderboard`: `/ranking`, the home Top 5 and `get_leaderboard` never read it.

**Flavor catalog: `src/content/sabores.ts` is the single source** — name, `base` and `color`, exported in alphabetical order. `base` (leche/agua) is shown to the public and matters to people who avoid dairy: confirm it with the shop, never guess it. The images in `public/sabores/` are **generated, never hand-placed**: `npm --prefix tools/brand-assets run sabores` writes them and deletes images of flavors no longer in the catalog. It recolors one of two neutral AI-generated base photos in `tools/brand-assets/fuentes/` — `base-leche` for milk flavors, `base-agua` for water ones — keeping their shape, texture and light and taking only the color from each flavor's `color` (a list paints bands, as for Napolitano). A flavor with its own photo in `fuentes/sabores/<id>.(png|jpg|webp)` uses it as is instead (today only Picafresa; the water flavors are meant to get theirs one by one). Without the two bases it falls back to a procedural render. Rerun it after changing a `color` or adding a flavor. With more than 12 visible, `/admin/flavors` shows them in even pages of up to 12 that rotate every 10 s.

**SEO: the public pages are prerendered at build time, and one manifest drives every `<head>`.** Before this, every URL served the same empty `<div id="root">`: crawlers and link previews (WhatsApp, Facebook, TikTok never run JS) saw a blank page with one shared title, `/sitemap.xml` and `/favicon.ico` returned the SPA shell, and any invented URL answered 200. The pieces:

- `src/seo/routes.ts` is the manifest: **one entry per `<Route>`**, with `kind` — `prerender` (static HTML with real content: `/`, `/generar`, `/login`, `/terminos`, `/privacidad`, `/eliminar-cuenta`, and `NOT_FOUND` → `404.html`), `spa` (served the empty `spa.html` shell with `noindex`: member, admin, `/bienvenida`, `/auth/callback`) or `redirect`. Title, description, canonical, robots, OG/Twitter and JSON-LD (`src/seo/schema.ts`) come from it. **Adding a `<Route>` means adding its manifest entry, and if it is `spa`, a rewrite to `/spa` plus an `X-Robots-Tag` rule in `vercel.json`.** `seo-check` fails the build on any mismatch between `<Routes>`, the manifest and `vercel.json`.
- `scripts/prerender.mjs` renders each `prerender` route with React 19's `prerender` (from `react-dom/static`, which waits for Suspense — `renderToString` would ship the fallback), writes `dist/<route>.html`, `404.html`, `spa.html` and `sitemap.xml`, and injects the head from the manifest between the `<!--seo:start/end-->` markers of `index.html`. `PRERENDER_MODE=shell` is the kill switch: correct heads, empty roots, everything mounts client-side.
- `src/main.tsx` **hydrates only when `#root[data-ssr-path]` equals the current path**, otherwise `createRoot`. `404.html` and `spa.html` never carry the attribute.
- On client navigation, `RouteTracker` calls `applyHead(seoForPath(pathname))` **before** `trackPageview`, so GA's `page_title` is the new page's. Never put `<title>`/`<meta>` in components: React 19 would hoist a second copy next to the prerendered one.
- `vercel.json` has **no catch-all rewrite — never add one back**: it brings back the soft 404s. `cleanUrls` serves `x.html` at `/x`, rewrites keep the query string (so `/auth/callback?code=…` → `spa.html` and PKCE works as before), and `404.html` is served with a real 404. `/assets/*` is `immutable` for a year.
- **Rules for anything a prerendered page renders** (Home, Redeem, Login, the legal pages, NotFound, and what they mount — Navbar, Footer, BottomNav, CookieBanner, the leaderboard): the first client render must equal the Node render, where there is no `window`, storage or `location` and the store has `authReady=false`, `profile=null`. So no `window`/`localStorage`/`sessionStorage`/`location`/`Date.now()`/`Math.random()`/`useSearchParams` with visible effect during render or in `useState` initialisers — do it in an effect. `useSyncExternalStore` always gets a server snapshot (without it the prerender throws). `useHydrated()` gates what must never be in the static HTML (the cookie banner).
- Heavy prerendered routes are split with `lazyWithPreload` (`src/lib/lazyWithPreload.ts`) and listed in `preloadByPath` (`AppRoutes.tsx`): `main.tsx` awaits the chunk **before** `hydrateRoot`, because a still-suspended boundary that receives an update mid-hydration is re-rendered client-side with its fallback. Plain `React.lazy` is fine only for `spa` routes, which are never hydrated.
- `src/content/negocio.ts` is the single source of the business NAP (name, address, phone, geo, Maps CID, social profiles): the footer, the home's location section and the `IceCreamShop` JSON-LD all read it, because Google cross-checks NAP consistency. **The footer shows only the alcaldía and the email, on purpose**: the street, C.P. and phone are the fiscal domicile and line of the owner, a natural person, so they stay in the home's location section, the legal pages and the JSON-LD instead of on every page. Don't put the full NAP back in the footer. `src/content/faq.ts` feeds both the visible FAQ and the `FAQPage` JSON-LD, so the text is plain and **must stay faithful to `legal/terminos.md`**. No opening hours, price range or delivery links are published: the owner has not decided them.
- `scripts/indexnow.mjs` submits the sitemap URLs to IndexNow (Bing/Yandex) after a deploy; its key file lives in `public/`.

**Styling:** Tailwind with a custom brand palette (`brand.navy/coral/lemon/cream/mint/pink`) defined in `tailwind.config.ts`, plus shared component classes (`.btn-coral`, `.btn-navy`, `.glass-card`, `.field-input`, `.qr-card`, `.points-chip`, etc.) defined in `src/index.css` under `@layer components`. Prefer these existing classes over ad hoc utility strings when building new UI. `cn()` in `src/lib/utils.ts` (clsx + tailwind-merge) is the standard way to compose conditional class names. `utils.ts` must stay light because everything imports it: the `date-fns` helpers live in `src/lib/fechas.ts` (only lazy pages use them), and `formatDateRange` uses `Intl`.

**Fonts are self-hosted** through `@fontsource` (`src/styles/fonts.css`, latin subset, only the weights in use), with metric-adjusted fallback faces generated by `tools/brand-assets` to keep the font swap from shifting layout. **Never load Google Fonts again**: privacy notice 2.2.1 states that the fonts are served from our own server and no longer hand the visitor's IP to Google. Doing it anyway makes the notice false; it needs a new legal version first.

**Legal text: `legal/*.md` is the single source, and it feeds BOTH repos.**

There are two documents — Términos y Condiciones and Aviso de Privacidad — plus an `aviso simplificado` marked `rol=simplificado` inside the privacy one. Mexican law treats the privacy notice as a separate instrument from the terms, which is why `/privacidad` exists as its own route.

The Markdown is never rendered: it is **compiled**. `scripts/lib/legal.mjs` parses a closed grammar (specified in `legal/README.md`) into an AST, and emits TypeScript here (`src/content/legal/generated/`) and Kotlin into the Android repo, plus a `legal.lock.json` that must be byte-identical in both roots. Neither platform has a Markdown parser and Android's version catalogue is frozen, so a structured AST was the only option; Markdown is just the authoring format, chosen so the `git diff` of a legal change reads as prose.

- `npm run legal:build` regenerates both repos. `npm run legal:check -- --cross` verifies. `prebuild` runs the check before every production build.
- **Never edit anything under a `generated/` directory.** Change the `.md`, bump `version`, regenerate. The checker fails loudly if you don't.
- The generator emits three TS artifacts: `legalContent.ts` (the full ASTs), `legalSimplificado.ts` (for `/bienvenida`) and `legalMeta.ts` (id, title, version, date, hash — no text). **Only the legal pages may import `legalContent.ts`**; `store.ts`, `LegalGate` and the SEO manifest read `legalMeta.ts`, which is what keeps ~50 KB of legal text out of every page's bundle.
- Any seeded version — even a patch — makes `my_legal_status` ask **every** user to accept again, because it compares exact versions; the MAJOR/MINOR/PATCH semantics in `legal/README.md` are not enforced by the server.
- **What changed, in two lines, goes on the gate.** `src/content/legal/novedades.ts` maps `id@version` to a headline ("Gran noticia") and bullets, and `LegalGate` shows them above the accept button for the pending documents. It is not legal text — not in the AST, not in the hash — but it must be faithful to the `.md`. Android mirrors it in `LegalGateStrings.kt`: **change it in one, change it in the other.** A release without an entry simply shows no box.
- **`:::alcance web|android` labels a block, it never hides it.** A `web` block still renders on Android, with a pill saying it doesn't apply there. That is what makes the hash mean something: with filtering, it would only prove the platforms agree on the parts each chose to show. The parser rejects any hiding syntax.
- The scope pill paints only when the scope **changes** from the previous block — a `:::alcance` fence flattens over several paragraphs, and without that rule the cookies section showed three identical pills. It is presentation derived from the AST, mirrored in both renderers. **Change it in one, change it in the other.**
- Both renderers are exhaustive by compiler: `const _exhaustive: never` in TypeScript, `when` as an expression over a sealed interface in Kotlin. The hash proves the data is identical; this proves both sides paint all of it.
- Publishing a version means seeding `legal_versions` with its `(doc_id, version, ast_hash)` — the generator prints the `insert`. **This is not the last step, it is a prerequisite**: `complete_signup` rejects any version it cannot find, so an unseeded version breaks every signup.
- The `aviso simplificado` opens with what is done with the data and **closes** with one line naming the responsable and their domicile. That line is the legal minimum, not decoration: LFPDPPP art. 16 fr. II requires identity and domicile (fr. I–IV of art. 15) in the simplified notice. It is kept discreet at the end because the responsable is a natural person; never drop it.
- `prebuild` refuses to build while the text still contains `«PENDIENTE: ...»` markers. They render literally on the page, and a notice that doesn't identify the responsable doesn't comply. `npm run dev` still works; `LEGAL_PERMITIR_PENDIENTES=1` is the escape hatch.

The Android repo's path is resolved via `.legalrc.json` (or `--android`, or `MADOS_ANDROID_REPO`). `.gitattributes` pins the legal files to LF in both repos, because the lock is compared byte for byte and the hashes are computed over LF.
